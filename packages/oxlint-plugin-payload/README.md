# oxlint-plugin-payload

Oxlint plugin that enforces [Payload CMS](https://payloadcms.com) best practices on Local API calls — so code written by hand or generated by AI agents is caught by `oxlint` instead of manual review.

Part of the [payload-lint](https://github.com/erikenz/payload-lint#readme) monorepo. Using Biome instead? See [`biome-plugin-payload`](https://github.com/erikenz/payload-lint/tree/main/packages/biome-plugin-payload#readme).

> [!NOTE]
> Oxlint JS plugins are alpha and not covered by semver. This package is tested against the oxlint version pinned in the monorepo. Pin a tested oxlint version in your project and upgrade deliberately.

## Rules

| Rule                               | What it catches                                                                                                                                                                                                           | Severity |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `no-find-without-select`           | `payload.find` / `payload.findByID` / `payload.findGlobal` / `payload.findVersions` / `payload.findVersionByID` calls that do not pass a `select` object, causing more fields than needed to be fetched from the database | `error`  |
| `no-find-without-depth`            | The same read operations that do not set `depth` explicitly — omitting it uses the application default (1), silently populating one level of relationships                                                                | `error`  |
| `no-missing-override-access`       | Any Local API call that does not declare `overrideAccess` explicitly — the Local API bypasses access control by default (`overrideAccess: true`)                                                                          | `error`  |
| `prefer-explicit-populate`         | Read operations with `depth` > 0 (numeric literal) that do not pass a `populate` object, so populated related documents return more fields than intended                                                                  | `error`  |
| `require-user-with-override-false` | Any Local API call with `overrideAccess: false` that does not pass `user`, `req`, or `user: null` — without a user object, access control functions receive `undefined` and behave unpredictably                          | `error`  |

All rules match any receiver that is the identifier `payload` or a member expression ending in `.payload` (e.g. `req.payload`, `this.payload`).

`prefer-explicit-populate` is a heuristic: it only fires when `depth` is a positive numeric literal (`depth: 2`). Shorthand (`depth`) and computed values (`depth: opts?.depth ?? 0`) cannot be verified statically and are skipped. If the target collection defines [`defaultPopulate`](https://payloadcms.com/docs/queries/select#populate) in its config, Payload already limits which fields are returned during population — suppress the diagnostic in that case with an `oxlint-disable-next-line` comment.

## Install

```sh
npm install --save-dev oxlint-plugin-payload
# or
bun add -d oxlint-plugin-payload
# or
pnpm add -D oxlint-plugin-payload
```

## Enable

Register the plugin under `jsPlugins` and enable the rules. The `name` can be any alias; `payload` keeps the rule IDs short. Because the plugin's `meta.name` is `payload`, a plain `"oxlint-plugin-payload"` entry also works, but the explicit alias is clearer.

```jsonc
// .oxlintrc.json
{
	"jsPlugins": [{ "name": "payload", "specifier": "oxlint-plugin-payload" }],
	"rules": {
		"payload/no-find-without-select": "error",
		"payload/no-find-without-depth": "error",
		"payload/no-missing-override-access": "error",
		"payload/prefer-explicit-populate": "error",
		"payload/require-user-with-override-false": "error"
	}
}
```

Or with `oxlint.config.ts`:

```ts
import { defineConfig } from "oxlint";

export default defineConfig({
	jsPlugins: [{ name: "payload", specifier: "oxlint-plugin-payload" }],
	rules: {
		"payload/no-find-without-select": "error",
		"payload/no-find-without-depth": "error",
		"payload/no-missing-override-access": "error",
		"payload/prefer-explicit-populate": "error",
		"payload/require-user-with-override-false": "error",
	},
});
```

## Intentional Anonymous Access (`overrideAccess: false`)

When making an intentional anonymous query in public Server Components (where no `user` or `req` session exists), pass `user: null` explicitly to communicate unauthenticated access without needing a suppression comment:

```ts
// Explicit unauthenticated query — access control functions run with user = null
const pages = await payload.find({
	collection: "pages",
	overrideAccess: false,
	user: null,
});
```

## Suppress an intentional violation

```ts
// oxlint-disable-next-line payload/no-find-without-select: full document intentionally needed here
const post = await payload.find({ collection: "posts" });

// oxlint-disable-next-line payload/prefer-explicit-populate: collection defines defaultPopulate
const post = await payload.find({
	collection: "posts",
	depth: 1,
	select: { title: true },
});
```

## Known limitations

- Only calls whose argument is an **object literal without spread** are analyzed. `payload.find(args)` and `payload.find({ ...base })` are skipped because the keys cannot be verified statically.
- `payload.db.*` direct-database calls are intentionally not covered.
- `prefer-explicit-populate` only fires when `depth` is a positive numeric literal — variable or computed depth values are skipped.
- Oxlint JS plugins are alpha. The plugin uses the standard ESLint-compatible `create(context)` API, but behavior can change between oxlint releases.

## Development

```sh
git clone https://github.com/erikenz/payload-lint
cd payload-lint
bun install
bun run test
```

Source lives in `packages/oxlint-plugin-payload/src/`. Tests in `packages/oxlint-plugin-payload/test/plugin.test.ts` run the real `oxlint` binary against the shared fixtures in `fixtures/` and assert the emitted diagnostics. The same fixtures are used by the Biome package, so both implementations are expected to report the same messages.
